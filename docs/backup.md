# Backup and restore

## What to back up

| Part | Where |
|------|-------|
| age key | **outside** the instance repository, e.g. password manager - without it, nothing in the repository can be decrypted |
| instance repository | settings (`variables.auto.tfvars`), OpenTofu state (`state/`), IAM configuration (`iam/`), IAM database backup (`backup/`) - push it |

That is all: a (shallow) clone of the pushed instance repository plus the age key restores the instance. If `backup/` is not committed, keep a copy of it, too. `output/` is not needed: it is regenerated by phase 2.

Two settings must never change or get lost:
- `sec_data_key` - the keys protecting data in the database (Airlock 2FA storage encryption, OATH OTP secrets) and the new-device cookie are derived from it. With the same value, a new installation gets the same keys and a database backup stays usable.
- `sec_state_passphrase` - encrypts the OpenTofu state.

## What is not backed up

| Data | After a recovery |
|------|------------------|
| IAM configuration | from `iam/` of the instance repository; changes made only in the Config Editor are lost - `make iam-config-pull` and commit before |
| IAM sessions (Valkey), Microgateway sessions | users log in again |
| emails in Mailpit, logs | lost |
| internal CA (`tls_issuer = "internal"`) | created anew by cert-manager - browsers need to trust the new CA, see [usage](usage.md#certificate-of-the-internal-ca) |
| Let's Encrypt certificate | issued anew |
| generated secrets (DB, Valkey, OIDC client passwords, OIDC signing key, ...) | generated anew if the state of phase 3 is gone - no impact on the data |

## Backup of the IAM database

```
export SOPS_AGE_KEY_FILE="${PWD}/age.keys"
make backup              # dump only
make backup COMMIT=1     # dump and commit
make backup PUSH=1       # dump, commit and push
```

The dump is written to `backup/iam-db.sql.gz.sops` (compressed, encrypted with the instance's age keys), overwriting the previous one - older versions are in the git history. `backup/iam-db.info` records the time and the release. Requires kubectl and `output/kubeconfig.yaml`.

Back up before demos that change data, before an upgrade and before removing the instance. Changes made in the Config Editor: `make iam-config-pull`, commit.

Planned: an optional backup to S3 by the MariaDB operator, enabled by S3 credentials in the settings. `make backup` stays available.

## Restore into a running instance

E.g. after a demo has messed up the data:
```
export SOPS_AGE_KEY_FILE="${PWD}/age.keys"
make restore
```

After confirmation, `make restore` pauses ArgoCD auto-sync (applications `bootstrap` and `iam`), stops IAM, loads the dump, starts IAM and resumes auto-sync. On failure, it starts IAM and resumes auto-sync, too.

The database is replaced completely, including the administrators: their passwords are those at the time of the backup, not `sec_password_iam`. Database users and grants are not part of the dump; they are managed by the MariaDB operator.

Restore only into the release recorded in `backup/iam-db.info`: the IAM database schema is not upgraded on restore. To get a backup into a newer release, restore it into the old release, then upgrade (change `release`, `make init`, apply).

## Recover a lost instance

E.g. the VM has been deleted or reset, or the instance moves to another machine:
```
git clone --depth 1 <instance-repository> && cd <instance>
export SOPS_AGE_KEY_FILE=<path to age.keys>
make init
make remove        # removes leftovers of phase 1, drops the state of phases 2 and 3
make build
make restore       # when ArgoCD has synced everything and IAM is running
git add state && git commit -m "Recovered" && git push
```

`make remove` destroys only phase 1 (VM, disks, network, cloud resources) - everything of phases 2 and 3 runs in the VM and vanishes with it, so their state is just dropped. Resources that no longer exist are removed from the state without error, so `make remove` works for a partly or completely lost instance. It removes only what is in the committed phase 1 state; if that state is missing or outdated, delete leftovers manually:
- azure: `az group delete -n <resource group>`
- kvm: `virsh destroy <name>`, `virsh undefine <name>`, `virsh vol-delete` for the VM's volumes
- local: the VM is managed manually

The platform's manual steps (see platform documentation) apply as for a new installation.

### Different platform or FQDN

The database backup can also be restored into an instance on another platform (e.g. local to azure) with the same settings, in particular the same `sec_data_key`. Then:
- passkeys are bound to `demo_fqdn` - with a different FQDN, users must register them again,
- Airlock 2FA devices keep working only with the same Futurae service (`airlock_iam_futurae`),
- OATH tokens keep working (`sec_data_key`),
- redirect URIs registered at external OIDC providers (e.g. an external administrator login) must match the new FQDN.

## Update an existing instance repository

Instance repositories created before backup/restore existed need:
1. the current `Makefile` from the [instance template](https://github.com/airlock-presales/airlock-iam-salesdemo-instance-template) (targets `backup`, `restore`, new `remove`),
2. the rule for `backup/` in `.sops.yaml` (see the instance template),
3. the IAM configuration `iam/iam-config.yaml`: `make init` creates it from the template; an instance that used the configuration of the base repository with its own changes (e.g. an external administrator login) copies that configuration instead,
4. the setting `sec_data_key` (`sops edit variables.auto.tfvars`, value e.g. `openssl rand -base64 48`). The first `make apply-3` afterwards replaces the Airlock 2FA storage, OATH and new-device keys once: Airlock 2FA and OATH registrations made before must be redone.
